# 로그인·권한 설계 (확정본)

2026-09-10 확정. 이 문서는 코드에 없는 "왜"를 담는다.
설계안 검토 뒤 확정된 내용이고, 여기서 벗어나는 구현은 이 문서를 먼저 고친 뒤에 한다.

---

## 결론 세 줄

1. **자체 구현.** Supabase Auth 를 쓰지 않는다.
2. **공통 관문 + 정책표.** 라우트마다 검사를 흩뿌리지 않고, 표에 없는 경로는 관리자만.
3. **잠그기는 맨 마지막.** 전원이 계정을 갖기 전에 잠그면 센터 업무가 멈춘다.

---

## 1. 왜 자체 구현인가

| 기준 | Supabase Auth | 자체 구현 |
| --- | --- | --- |
| 이름+코드 로그인 | 이메일·전화가 사실상 전제. `이름@ok.local` 같은 가짜 주소가 데이터 모델에 남는다 | 이름이 그냥 열쇠다 |
| 초대코드 → 비번 설정 | 대응하는 기본 흐름이 없다 | 처음부터 우리가 만드는 것이 전부다 |
| 사람 표 | `auth.users` 와 `staff` 가 갈라진다. 퇴사·삭제 때 두 곳을 맞춰야 한다 | `staff` 한 곳 |
| 얻는 값 | 가장 큰 값은 JWT ↔ RLS 연동인데 **우리는 RLS 를 안 쓴다**(원칙 4). 브라우저 SDK 도 원칙 4 때문에 못 쓴다 | 안 쓸 것에 치를 값이 없다 |
| 즉시 차단 | JWT 는 만료 전까지 산다. 결국 차단 목록을 따로 둔다 | 세션 행을 지우면 그 순간 끝 |
| 직접 짜는 위험 | 남이 짜 준다 | 비번 해시 한 함수 + 세션 표 하나. 방식이 정해져 있어 창의력이 들어갈 자리가 없다 |

마지막 줄만 Supabase 쪽이 낫다. 나머지 다섯 줄이 더 크다.

## 2. 확정된 값

| 항목 | 값 | 어디에 |
| --- | --- | --- |
| 비번 해시 | PBKDF2-HMAC-SHA256, **60만 회**, 소금 16바이트 | `lib/password.ts` |
| 저장 모양 | `pbkdf2$600000$<소금 b64>$<해시 b64>` | 알고리즘·횟수를 값 안에 넣어 나중에 올릴 수 있게 |
| 비번 규칙 | **최소 8자.** 기호·대문자 강제 없음. 흔한 비번 몇 개와 이름 그대로만 거부 | 강제하면 포스트잇에 적힌다 |
| 초대코드 | 숫자 6자리, **해시 저장**, 1회용, **만료 30일** | 격주로 오는 봉사자도 받을 수 있게 |
| 시도 제한 | **5회 실패 → 15분 잠금** | 6자리는 100만 가지뿐이라 시도 제한이 곧 자물쇠 |
| 세션 | 32바이트 난수 토큰, DB 에는 **SHA-256 만** | JWT 아님 — 정지시키면 그 자리에서 끊겨야 한다 |
| 쿠키 | `HttpOnly; SameSite=Lax; Path=/`, https 일 때만 `Secure` | `SameSite=Lax` 가 CSRF 를 막아 토큰을 따로 안 둔다 |
| 세션 만료 | **쉬는 시간 8시간 / 절대 30일** | 8시간이 하루 근무와 맞는다 |
| 동명이인 | **비번 검사 없이 거부** + `login_name` 으로 관리자가 해소 | 한쪽이라도 맞춰 보면 어느 쪽이 맞는지 새어 나간다 |
| 감사 로그 컨텍스트 | `AsyncLocalStorage` | 아래 4절 — 검증 통과 조건부였고, 통과했다 |
| 관문 켜고 끄기 | `AUTH_ENFORCE` 환경변수 | `true` 면 막는다. 비었거나 `false` 면 **최초 부팅이 끝나는 순간부터 막는다**(그 전에만 경고). `warn` 은 끝까지 경고만 — 비상 되돌리기 전용. 되돌릴 때 배포를 안 건드려도 된다(2026-09-17 맨땅 점검 뒤 바꿈 — 예전 `false` = 경고만) |

> **실운영 전환 시 전원 재발급이 원칙이다.**
> 지금 붙어 있는 계정은 개발 중에 만든 더미이고 그 비밀번호는 대화·로그에 평문으로 남아 있다.
> 실제로 쓰기 시작하는 날 관리자부터 순서대로 [비번 재설정]으로 새 코드를 받아 다시 정한다.
> 관리자를 마지막에 하면 중간에 잠긴다 — 관리자를 먼저, 그 다음 나머지.

### 세션 토큰은 왜 PBKDF2 가 아닌가

사람이 고른 값이 아니라 32바이트 난수다. 추측할 여지가 없어 느리게 만들 이유가 없고,
요청마다 도는 계산이라 빨라야 한다. SHA-256 한 번이면 충분하다.

### `Secure` 쿠키의 함정

`http://localhost` 에 `Secure` 를 붙이면 브라우저가 쿠키를 **아예 저장하지 않는다.**
로그인은 성공하는데 다음 요청에서 곧바로 튕기고, 원인이 눈에 안 보인다.
그래서 요청이 https 일 때만 붙인다(`api/cookie.ts`). 애저 Container Apps 는 수신부가 TLS 를 풀고 앱에는 http 로 넘기므로 `X-Forwarded-Proto: https` 도 https 로 본다. 구 스택(Deno Deploy)은 늘 https 였다.

## 3. 세 축과 권한 4단계

세 축은 서로 다른 일을 한다.

| 축 | 컬럼 | 무엇을 정하나 |
| --- | --- | --- |
| 직급 | `staff.role` | 무슨 일을 하는 사람인가 |
| 관리자 깃발 | `staff.is_admin` | 설정과 계정 발급을 만질 수 있는가 |
| 접속 권한 | `staff.access_kind` | PC 화면인가 모바일 화면인가 |

**권한 4단계는 컬럼이 아니라 파생이다** (`lib/permission.ts` 의 `levelOf`).
따로 저장하면 직급을 바꿨는데 등급은 그대로인 어긋남이 생기고, 그 어긋남은 조용하다.

| 등급 | 조건 | 할 수 있는 것 |
| --- | --- | --- |
| 관리자 | `is_admin = true` | 전부 + 계정 발급 + ⚙설정 |
| 센터장 | `role = '센터장'` | 종사자 전부 + 계정 발급. 설정은 못 본다 |
| 종사자 | `role = '생활복지사'` | 업무 전부. 설정·계정 발급 불가 |
| 봉사 | 멘토·봉사자, 그리고 직급을 모르는 사람 | 모바일 기능만. 본인 것 + 반기 관찰 작성 |

`access_kind` 는 이 등급과 **직교**한다. "생활복지사인데 모바일만" 같은 조합이
가능해야 축을 나눈 뜻이 산다.

관리자는 **여럿이어도 된다.** 하나뿐이면 그 사람이 비번을 잊는 순간 아무도 계정을
만들 수 없다. 실운영은 관리자(생활복지사)와 센터장 둘에 깃발을 붙인다.

### 계정 상태를 두 값만 저장하는 이유

화면에는 네 가지로 보이지만 DB 에 담는 것은 `활성`/`정지` 둘뿐이다.

| 화면 | 어디서 나오나 |
| --- | --- |
| 미발급 | 비번 없음 + 코드 없음 |
| 대기 | 비번 없음 + 코드 있음 |
| 활성 | 비번 있음 |
| 정지 | `account_status='정지'` 또는 `staff.status='종료'` (위 무엇이든 이긴다) |

상태를 따로 저장하면 비번을 설정했는데 상태는 '대기' 로 남는 어긋남이 생긴다.
`account_status` 는 "사람이 막았는가" 하나만 담는다.

**로그인이 되려면 네 가지가 모두 참이어야 한다** — `staff.status='활동중'`,
`account_status='활성'`, `password_hash` 있음, `locked_until` 지남 또는 없음.

## 4. 감사 로그의 "누가"

`db/audit.ts` 가 이미 못 박아 두었다: *"전역 변수가 아니라 요청 컨텍스트로 넘겨야 한다 —
두 요청이 섞이지 않게."* 그대로 따른다.

**`AsyncLocalStorage`를 쓴다** (`lib/request_context.ts`). 인자로 명시적으로 넘기면
39개 API 핸들러와 그 아래 `/db` 함수 대부분의 시그니처를 고쳐야 한다 —
`recordAudit` 은 삭제·수정 함수 깊은 곳에서 불린다.

채택 조건은 **동시성 검증 통과**였다. `lib/request_context.test.ts` 가 그 검증이고,
2026-09-10 에 7건 전부 통과했다(동시 2건·동시 10건·중첩·누출 없음).
이 테스트가 한 줄이라도 깨지면 방식을 바꿔야 한다는 신호다 — 지우지 말 것.

## 5. 붙이는 순서

원래 제안(①인증 → ②잠금 → ③계정 관리)에서 **계정 관리를 잠그기 앞으로 옮겼다.**
그 순서면 잠그는 순간 계정이 있는 사람은 최초 관리자 한 명뿐이고, 나머지 직원은
계정 관리 화면이 생길 때까지 아무도 못 들어온다.

| 단계 | 무엇 | 끝난 뒤 상태 |
| --- | --- | --- |
| 0 | 마이그레이션 022 | 지금과 완전히 같이 동작 |
| 1 | 인증 기반 — 비번·코드·세션·`/login`·최초 부팅 | 로그인은 되지만 **아무것도 안 잠긴다** |
| 2 | 계정 관리 화면 | 전원이 계정을 가질 수 있다. 여전히 안 잠긴다 |
| 3 | 감사 로그 actor 채우기 | 삭제·수정에 이름이 남는다 |
| 4 | 관문 — **경고만** (당시 `AUTH_ENFORCE=false`, 지금은 `warn`) | 동작은 그대로. 정책표의 빈틈이 로그로 드러난다 |
| 5 | 잠근다 (`AUTH_ENFORCE=true`) | 로그인해야 쓸 수 있다. 환경변수 하나(`warn`)로 되돌린다 |
| 6 | 봉사자 범위 — 본인 것만 | 봉사자가 폰으로 자기 것만 본다 |

**5단계로 넘어가는 기준**: 계정 관리 화면의 "대기 n명 · 미발급 n명" 이 0 이 되고,
설정 > 관문 경고가 비어 있을 때. 둘 다여야 한다 — 앞은 사람이 못 들어오는 것을 막고,
뒤는 화면이 못 도는 것을 막는다.

**봉사자 계정은 로그인은 되고 PC 화면만 막힌다.** 설계 초안에서는 로그인 자체를 막으려
했지만, 그러면 6단계 전까지 계정이 살아 있는지 확인할 방법이 없다. 지금은 들어와서
"아직 준비 중입니다" 를 보게 한다 — 빈 화면보다 낫다.

5단계에서 함께 나가야 하는 셋 — `AUTH_ENFORCE=true`, `ui.js` 의 401 → `/login`,
`/` 접근 시 세션 없으면 `/login` 302. **한 배포에 같이** 나가야 한다.

## 6. 위험 지점

| 잘못하면 | 이렇게 된다 | 조치 |
| --- | --- | --- |
| 계정을 다 만들기 전에 잠근다 | 최초 관리자 말고 아무도 못 들어온다 | 5절 순서. `AUTH_ENFORCE=warn` 으로 즉시 되돌린다 |
| 경고 모드로 부팅하고 잠그는 것을 잊는다 | 부팅 뒤에도 로그인 없이 명단·계정 API 가 열린 채 | 비었거나 `false` 면 부팅이 끝나는 순간 자동 잠금(`api/guard.ts` · `api/boot_state.ts`). 끝까지 여는 것은 `warn` 뿐 |
| 관리자가 비번을 잊는다 | 코드를 재발급해 줄 사람이 없다 | 관리자를 **둘 이상** 둔다. 최후에는 아래 비상 절차 |
| 정적 파일까지 관문에 건다 | 로그인 페이지가 제 CSS 를 401 로 못 받는다 | 관문은 `/api/*` 에만 |
| 401 처리를 빼고 잠근다 | 세션 만료 시 화면이 "서버 오류" 만 여러 개 띄우고 멎는다 | 잠금과 **같은 배포**에. 여러 번 안 보내는 가드 |
| `Secure` 를 로컬에서도 붙인다 | 로그인해도 바로 튕긴다 | https 일 때만 (`api/cookie.ts`) |
| 최초 부팅을 화면에서만 막는다 | 누구나 관리자를 만든다 | 서버가 다시 확인 + `settings` 자리 선점 |
| 초대코드를 평문으로 둔다 | DB 를 한 번 보면 전 계정을 가져간다 | 해시 저장 + 30일 만료 + 5회 15분 |
| 동명이인에게 비번을 검사한다 | 어느 쪽이 맞는지 새어 나간다 | 검사 없이 거부 |
| 컨텍스트가 요청 사이에 샌다 | 감사 로그가 남의 이름으로 남는다 — 조용히 틀린다 | `lib/request_context.test.ts` |
| 정책표를 빠뜨린 새 API | 기본값이 "열림" 이면 뚫린 채로 산다 | 기본값 **관리자만**. 잊으면 403 이 나서 눈에 띈다 |
| 공용 PC 에서 로그아웃을 안 한다 | 앞사람 이름으로 일지가 쓰인다 | 앱바에 이름을 늘 크게. 쉬는 시간 8시간 |

### 비상 절차 — 관리자가 잠긴 경우

배포 DB 에서 직접 초대코드를 넣는다. 해시가 필요하므로 서버에서 만들어야 한다.

```
deno eval --env-file 'import { hashSecret } from "./lib/password.ts"; console.log(await hashSecret("123456"));'
```

나온 값을 `staff.invite_code_hash` 에 넣고 `invite_code_expires_at` 을 미래로,
`account_status='활성'`, `locked_until=null` 로 둔다. 그 뒤 `/login` 에서
이름 + `123456` 으로 비번을 다시 정한다. **쓰고 나면 그 코드는 소진된다.**

## 7. 파일 지도

| 파일 | 하는 일 |
| --- | --- |
| `lib/password.ts` | 해시·검증·초대코드·세션 토큰. 아무것도 import 하지 않는 잎 모듈 |
| `lib/permission.ts` | 등급·계정 상태 계산. 잎 모듈 |
| `lib/request_context.ts` | 요청 하나에 "누구인가" 를 맨다 |
| `db/accounts.ts` | `staff` 의 로그인 칸. 해시는 이 파일 밖으로 안 나간다 |
| `db/sessions.ts` | 세션 표 |
| `api/cookie.ts` | 쿠키 굽기·지우기. auth 와 guard 가 같이 쓴다 |
| `api/guard.ts` | 쿠키 → 세션 → 사람 + 정책표로 판단. `AUTH_ENFORCE` 를 여기서 읽는다 |
| `api/policy.ts` | 정책표. 표에 없는 경로는 관리자만 |
| `api/warnings.ts` · `api/guard_warnings.ts` | "막혔을 요청" 을 모아 두는 자리와 그 API |
| `web/assets/guard_warnings.js` | 설정 > 관문 경고 화면 |
| `api/auth.ts` | 로그인·로그아웃·첫 비번·최초 관리자 |
| `api/accounts.ts` | 계정 관리. **5단계에서 관리자·센터장 전용** |
| `web/login.html` · `web/assets/login.js` | 로그인 페이지 (index.html 과 별도) |
| `web/assets/accounts.js` | 계정 관리 화면 |
| `web/assets/me.js` | 앱바의 지금 사용자 |

### 왜 로그인이 별도 페이지인가

`index.html` 은 열리자마자 화면 모듈을 전부 import 하고 API 를 예닐곱 개 때린다.
로그인 전에 그 파일을 열면 아직 답할 수 없는 요청이 우수수 나간다.
